# Обоснование событийного подхода vs Camel / DWH

1. **Децентрализованная логика.** Бизнес-правила живут в bounded context, а не в ESB. Домены развиваются независимо - без согласования каждого изменения с центральной интеграцией.

2. **Лёгкое расширение.** Новый потребитель подключается подпиской на событие (Schema Registry), без новых Camel-маршрутов и ETL в общий DWH.

3. **Меньше синхронных связей.** Между доменами - асинхронная доставка событий; синхронные вызовы только там, где это явно нужно по контракту (например, доступ к `payloadRef` / `resultRef`).

4. **Локальные проекции.** Потребитель строит read model из потока - меньше запросов в чужие системы, удобная схема, выше отзывчивость, ясное владение.

5. **Границы доменов (DDD).** OHS, ACL, Conformist задают, кто владеет контрактом и кто адаптируется. Один термин в разных доменах - разные модели; связь через id и события, без общей БД.

6. **Backpressure и масштабирование.** Kafka буферизует нагрузку между издателем и потребителем; consumer groups масштабируются горизонтально - в отличие от бутылочного горлышка ESB и batch DWH.

7. **Потоковая аналитика.** Тот же поток событий питает мониторинг, near-real-time витрины и обнаружение аномалий - без отдельной батч-загрузки в DWH.

8. **Аудит.** Append-only журнал событий - хронология фактов для расследований и регуляторов; проще, чем разрозненные логи маршрутов Camel.
